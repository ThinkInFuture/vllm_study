知识页 · SFA-C8 是什么

代码基线：precision-rca/vllm-ascend-git（main，e89f87ddb）· 主文件 vllm_ascend/attention/sfa_v1.py

一句话：enable_sparse_sfa_c8=true（简称 sfa_c8）让 GLM-5.1 这类稀疏注意力模型在 NPU 上， 把 SFA（Sparse Flash Attention）主注意力的 KV Cache 打包成 int8/fp8 量化布局，供专有算子 npu_kv_quant_sparse_flash_attention 消费 —— 目的是省 KV 内存、提升长上下文吞吐。 它是性能/内存优化开关，不是功能开关。

1 · 背景：GLM-5.1 的稀疏注意力架构（DSA）

GLM-5.1 的模型类型是 glm_moe_dsa（sfa_v1.py L401 显式判断），采用 DeepSeek V3.2 式的 稀疏注意力架构，两个组件配合：

组件作用对应代码
Lightning Indexer（轻量索引器）对每个 query，从全部 KV 块里快速挑出 top-k 个重要块（index_topk），决定注意力"看哪里"self.indexer / use_torch_npu_lightning_indexer=True（glm_moe_dsa 专属，L402-404）
SFA 主注意力（Sparse Flash Attention）只对索引器选中的 top-k 块做精确注意力计算AscendSFAImpl（L408）→ NPU 算子 npu_kv_quant_sparse_flash_attention

哪些模型走 SFA：model_uses_sfa_sparse()（utils.py）—— hf config 含 index_topk 且无 compress_ratios 即判定为 SFA 模型。GLM-5.1（glm_moe_dsa）与 DeepSeek V3.2 系都属于此类。

2 · C8 的两层含义（源码注释原文）

sfa_v1.py L507-511 的注释是理解这个开关的钥匙：

# Sparse C8 has two independent meanings in SFA:
# - SFA packed KV cache for npu_kv_quant_sparse_flash_attention.
# - C8 indexer cache for lightning indexer.
# The user-facing switches control these layouts independently. LI C8
# applies only to layers that own an indexer cache.
开关量化对象消费算子
enable_sparse_sfa_c8（本案开的）SFA 主注意力的 packed KV Cache：把 k_nope（量化压缩维）+ k_pe（rope 维）打包进单个量化张量npu_kv_quant_sparse_flash_attention
enable_sparse_li_c8（独立开关）Lightning Indexer 的索引缓存（只对拥有 indexer cache 的层生效）indexer 算子

GLM-5.1 的 128k/198k 两个配置：都开 li_c8，差别只在 sfa_c8 —— 即 198k 额外把主注意力的 KV 也做成 int8 量化打包。

3 · 打包后 KV Cache 布局改变（代码里的布局表）

sfa_v1.py L538-548：开启 Sparse C8 后，KV cache 张量元组的槽位排列会变：

================  ===========  ===========  =============  ==============
Layout            kv_cache[0]  kv_cache[1]  kv_cache[2]    kv_cache[3]
================  ===========  ===========  =============  ==============
Default           k_nope       k_pe         indexer_k      indexer_scale
Sparse C8         packed_kv    indexer_k    indexer_scale  (unused)
================  ===========  ===========  =============  ==============

即：sfa_c8 开启后，k_nope 与 k_pe 被量化打包成一个 packed_kv，indexer 缓存整体前移一位。 任何按旧槽位读取缓存的代码（KV 迁移、offload、P/D 分离传输）都需要适配这个布局。

4 · 量化数据类型（依硬件能力分支）

if enable_sparse_sfa_c8 or enable_sparse_li_c8:            # L514
    if get_current_hardware_profile().supports(FP8_ATTENTION):
        self.c8_k_cache_dtype     = torch.float8_e4m3fn    # FP8 平台
        self.c8_k_scale_cache_dtype = torch.float32
    else:
        self.c8_k_cache_dtype     = torch.int8             # A3 等平台
        self.c8_k_scale_cache_dtype = torch.float16

"C8" 即 8-bit 量化 KV：目标平台支持 FP8 注意力则用 e4m3fn，否则用 int8 + fp16 scale。

5 · 开关的生效条件（不是想开就开）

# ascend_config.py（pydantic 定义，默认 False）
enable_sparse_sfa_c8: bool = False
enable_sparse_li_c8:  bool = False

# 生效前的与运算（ascend_config.py 后处理）：
use_sparse = model_uses_sfa_sparse(vc.model_config)   # 模型必须是 SFA 稀疏类
self.enable_sparse_sfa_c8 = self.enable_sparse_sfa_c8 and use_sparse
self.enable_sparse_li_c8  = self.enable_sparse_li_c8  and use_sparse
  • yaml 里写 "enable_sparse_sfa_c8": true → 经 additional-config 注入 AscendConfig；
  • 仅当模型是 SFA 稀疏类（含 index_topk）才真正生效；
  • 相关辅助机制：量化时伴随 Hadamard 变换（q_hadamard / k_hadamard，dsa c8 启用时共享，L414/L625/L629），用于降低量化离群影响。

7 · 为什么开了会出问题 —— 数据流走读与薄弱点（结合回归窗口）

SFA-C8=true 的一次 decode，KV 数据要经过四步（全部在 sfa_v1.py）：

步骤做什么出错后果
① 量化写入新 token 的 KV 经 prolog v3 量化（int8 + fp16 scale，A3 平台），按 kv_slot_mapping 写入 packed_kv（k_nope+k_pe 打包 + Hadamard 变换）slot 错位 / scale 算错 → 之后每次检索读到的都是"错位的错值"
② 稀疏检索Lightning Indexer 用 indexer_k/indexer_scale（li_c8 量化缓存）为每个 query 选 top-k 块检索偏 → 注意力看错地方 → 答非所问
③ 反量化注意力npu_kv_quant_sparse_flash_attention 对选中块反量化并计算注意力反量化 scale 用错 → 输出数值系统性偏差
④ 输出投影W_UV 投影（按 token 数 ≤1024 与否分支选 batch_matmul_transpose / npu_transpose_batchmatmul）两个分支均为标准 matmul，低嫌疑

对照回归窗口 diff（git diff 85625bd7 e6a133f7 -- vllm_ascend/attention/sfa_v1.py），这段数据流里有三处恰好被重构过的薄弱点： ① 的 slot mapping 被统一重写（SFAForwardContext.kv_slot_mapping 取代旧的 DSACPContext 等多字段）、 Hadamard 共享静态张量的初始化时序变动、 Impl 选择改为运行时 resolve_sfa_impl() 动态解析 —— 三个机制级怀疑（M1 slot 错位 / M2 Hadamard 缓存污染 / M3 Impl 漂移）的详细论证见 ③ 可疑点 · 1b 节。
