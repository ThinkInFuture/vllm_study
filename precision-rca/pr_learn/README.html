Part A · 先教你看：一个 PR 页面长什么样

打开本目录任何 pr_*.html 快照（就是 GitHub PR 页面），从上到下看这五样东西：

看哪里是什么怎么判断
① 标题栏标题 #编号，旁边一个状态徽章徽章：Open 还在审 / Merged 已合入 / Closed 被关闭（未合入）
② 描述区（第一条评论）作者写的"这个 PR 做什么 / 为什么 / 怎么测的"。本仓库强制模板三段式看第一段就知道这个 PR 的目的
③ 标签页Conversation（讨论时间线）· Commits（提交历史）· Checks（CI 结果）· Files changed（代码差异）看懂改了什么 → Files changed；看为什么没合 → Conversation
④ Merge 框讨论区底部的合并按钮框绿勾=可合；"has conflicts" = 和主分支冲突，必须先解决（本目录 #16004 就卡在这）
⑤ 机器人评论github-actions[bot]（CI/格式提示）、gemini-code-assist[bot]（AI 代码摘要）"This pull request has conflicts" 这类机器人消息经常是状态关键
三种结局怎么读：Merged = 代码进入主分支；Closed 未合入 = 不合了 —— 原因通常在最后几条评论（功能废弃 / 长期无响应 / 方案被替代）；Open = 还在流程里（等 review、等改冲突、等 CI）。

Part B · 三个 PR 逐个解读

案例 1 · PR #15978 Merged 已合入 —— 教你认识"Backport（回移植）"

作者 / 时间Dawn952 · 09-07 创建，09-08 合入（1 天，极快）
改动规模+606 / -86，7 个文件，2 commits
做了什么把主分支的 #15416（Kimi K3 KDA 混合精度投影优化）回移植到 releases/v0.27.1rc 发布分支：加载权重后把 f_proj.weight = f_b_proj.weight @ f_a_proj.weight 现场合成，并把 beta / F 投影 / 输出门打包成一个 BFG 投影
知识点：Backport 是什么——新功能先在 main 分支落地（就是 #15416，我们在可疑点页查过它的同族 commit 222677fc）， 然后把修复"搬"到旧的发布分支（v0.27.1rc），让已发布的版本也能享受。所以你会看到同一个标题出现两次、 PR 描述里写着 "Backport #15416 to releases/v0.27.1rc"。Backport PR 几乎必合（维护者自己搬的），审查也快。

快照：pr_merged_15978.html · 数据：pr_data.json

案例 2 · PR #16004 Open 待合入 —— 教你认识"conflicts 卡住"

作者 / 时间Eric-dot · 09-08 创建（就在昨天）
改动规模+2171 / -51，17 个文件 —— 大改动
做了什么给 KV Pool 的 layerwise 传输适配 Mooncake 的 range sessions（分布式 KV 缓存传输协议的会话范围接口）
当前卡在哪机器人明确提示 "This pull request has conflicts" —— 主分支这几天动了同一片代码（17 文件的大 PR 很容易撞），作者需要 rebase/解冲突后才能进入正式 review
知识点："待合入"不等于"会合入"——Open 状态只代表流程未结束。判断 Open PR 的真实前景看三样： 是否有 conflicts、是否有人（maintainer）留了 review、CI Checks 是否在跑。 这个 PR 昨天刚建、有冲突、正文模板还没填完 —— 属于早期阶段。

快照：pr_open_16004.html

案例 3 · PR #7255 Closed 未合入 —— 教你认识"功能废弃型拒绝"

作者 / 时间线NJX-njx · 3 月 14 日创建 → 5-28 机器人报冲突 → 6-03 reviewer 说"方案可以，先解冲突" → 9-08（今天）被关闭，存活 6 个月
改动规模+14 / -1，2 个文件 —— 改动极小
做了什么修复 npu_weight_quant_batchmatmul 只接受 2D 输入的问题：3D 张量先转 2D、算完再转回来（关联 issue #3210）

03-14 创建，CI 机器人例行打招呼

05-28 机器人：与主分支冲突了

06-03 作者 @ 维护者 kunpengW-code；维护者回："LGTM，按建议的方式改，冲突需要解决" —— 看起来要合了

09-08 维护者："W4A8 线性量化在新版本中已被弃用，此 PR 暂时可以先关闭了" → 关闭

知识点：拒绝 ≠ 写得差——这个 PR 质量没问题（改动小、reviewer 都说 LGTM）， 它死于目标代码被废弃：它修的是 W4A8 线性量化的算子，而新版本把 W4A8 线性量化整条路扔掉了。 读 Closed PR 时，翻到最后一条人类评论基本就是答案。
顺带一提：这个 PR 的主题（batch matmul 量化算子）和我们正在追的头号嫌疑 _v_up_proj 新算子是同家族 —— 这个仓库里 batch matmul 类自定义算子的更替一直很频繁。

快照：pr_rejected_7255.html
